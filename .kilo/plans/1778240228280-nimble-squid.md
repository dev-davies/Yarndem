# Message Not Appearing Until Refresh - Root Cause Analysis & Implementation

## Problem Description

Incoming messages do not appear in the recipient's message window until the page is refreshed. The messages are being received via WebSocket but are not displayed in real-time.

## Root Cause Identified

### Issue 1: Inconsistent Conversation Key Generation

The `conversationKey` function was using `currentUser.value?.id` inline, which could be `null` during async operations. This caused:
- Messages saved via WebSocket to use one key (e.g., `'me:userB'` or different key formats)
- Messages loaded via `loadHistory` to use a different key format
- Mismatch between saved and loaded messages

### Issue 2: Potential Null CurrentUser During WebSocket Handler

The `currentUser.value` could be null/undefined when the WebSocket message handler runs (race condition during auth or session loading), causing the `otherUserId` calculation to be incorrect.

## Implementation Summary

### Changes Made to `app/composables/useMessages.ts`

1. **Added `getMyId` helper function** (line 43):
   ```typescript
   const getMyId = (): string | null => currentUser.value?.id ?? null
   ```

2. **Updated `conversationKey` to accept optional `myId` parameter** (lines 45-49):
   ```typescript
   const conversationKey = (otherUserId: string, myId?: string | null): string => {
     const me = myId ?? getMyId()
     if (!me) return 'unknown:' + otherUserId
     return [me, otherUserId].sort().join(':')
   }
   ```

3. **Fixed WebSocket message handler** (line 186):
   - Changed `conversationKey(otherUserId)` to `conversationKey(otherUserId, myId)`
   - This ensures consistent key generation using the same `myId` that was used to calculate `otherUserId`

4. **Fixed `loadHistory` function** (line 260):
   - Changed `conversationKey(userId)` to `conversationKey(userId, getMyId())`
   - Ensures the same key format is used when loading

5. **Fixed `sendMessage` function** (line 435):
   - Changed `conversationKey(toUserId)` to `conversationKey(toUserId, getMyId())`
   - Consistent key for outgoing messages

## How This Fixes the Issue

1. **Consistent Key Generation**: All messages (incoming WebSocket, history load, outgoing) now use the same conversation key format by explicitly passing `myId` or calling `getMyId()` at the point of use.

2. **No Silent Fallback to 'me'**: The old code would use `'me'` as a fallback when `currentUser.value?.id` was null, causing key mismatches. The new code returns a consistent format but also handles the null case gracefully.

3. **Immediate Message Display**: When `loadHistory` is called, it will now find messages saved via WebSocket because they have the same conversation key. Additionally, when a message arrives for the active conversation, it's added to `messages.value` immediately (line 221).
